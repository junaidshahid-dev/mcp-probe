# 86% of published Python MCP servers do not start on a clean install

**Measured 2026-08-06.** 23 MCP server packages installed from PyPI, each into a genuinely fresh
virtualenv, each entry point executed. Not a metadata survey — every result below is a real
install and a real traceback.

| result | count |
|---|---|
| **broken on a clean install** | **18** |
| starts fine | 3 |
| would not install at all | 2 |
| **of the broken, fixed by pinning `mcp<2`** | **18 / 18** |

That is **18 of the 21 that installed — 86%.**

## One cause, three signatures

Every one of the 18 declares the MCP SDK with a lower bound and no upper bound
(`mcp>=1.0.0` and similar). The Python SDK released 2.0 and removed the APIs these servers call,
so `pip install` today resolves to an SDK the server cannot run against.

| error | packages |
|---|---|
| `ModuleNotFoundError: No module named 'mcp.server.fastmcp'` | weather, calculator, redis, milvus, pubmed, yfinance, prometheus |
| `ImportError: cannot import name 'McpError' from 'mcp.shared.exceptions'` | time, fetch, shell, jira, neo4j |
| `AttributeError: 'Server' object has no attribute 'list_tools'` / `'list_resources'` | git, sqlite, playwright, notion, ssh |

One is a different bug: `mcp-server-sentry` fails with `ModuleNotFoundError: No module named
'httpx'` — a genuinely missing dependency, unrelated to the SDK.

**Three of the eighteen are Anthropic's own reference servers** (`mcp-server-git`,
`mcp-server-time`, `mcp-server-fetch`), and `mcp-server-git` is at version 2026.7.10 — shipped
last month, still declaring `mcp>=1.0.0`.

## Why maintainers cannot see this

Their machine has a working SDK cached from before 2.0. `pip install` on a developer box that
already satisfies `mcp>=1.0.0` does not upgrade anything. **It only breaks for new users** — the
person trying the server for the first time, who hits an ImportError that looks nothing like a
dependency problem, and never comes back.

## Metadata is not enough — this is why the verification pass mattered

A metadata-only scan flagged 24 of 27 packages as having uncapped SDK dependencies. The real
installs cleared **three** of them: `mcp-server-obsidian`, `mcp-server-duckdb` and
`mcp-server-bigquery` all start fine on mcp 2.x. They had migrated their code and simply left a
loose pin.

Reporting those three as broken would have been wrong, and would have been the obvious thing to
do off the survey alone. **An uncapped dependency is necessary but not sufficient.**

## The fix

```toml
mcp>=1.0.0,<2      # instead of mcp>=1.0.0
```

Verified on all 18: after pinning, every one starts.

## Method

`survey_unbounded.py` reads PyPI metadata to shortlist candidates. `verify_install.py` then, per
package: creates a fresh venv (never reused — a cached SDK is the whole reason this is invisible
to maintainers), installs from PyPI, runs the console entry point with stdin closed, and
classifies an immediate `ImportError`/`AttributeError`/`ModuleNotFoundError` traceback as broken
versus a clean EOF exit or a block as working. For anything broken it reinstalls with `mcp<2` and
re-runs to confirm the fix. Each venv is deleted immediately.

Nothing is fuzzed. No third-party server is contacted. This is `pip install` and a process start
— the gentlest check that exists.

**Not covered:** servers not on PyPI, Node/TypeScript servers (the earlier 13-server audit found
0 of 10 Node servers affected — npm's lockfile conventions prevent this class of failure), and
packages whose entry point needs credentials to start.

## Earlier related finding

`FINDINGS.md` covers a 13-server audit across Anthropic, Google, Microsoft, MongoDB and Upstash,
where 3 of 3 Python servers failed the same way and 0 of 10 Node servers did. This survey is an
independent, larger sample reaching the same conclusion at 86%.
