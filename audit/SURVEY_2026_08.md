# About 43% of Python MCP servers on PyPI don't start on a clean install

**Measured 2026-08-06/07.** Two stages, both reproducible, raw results in this repo.

## The headline number, with its denominator

PyPI carries **17,995 packages** with `mcp` as a name token (of 865,752 total, indexed
2026-08-07). A hand-picked list would prove nothing, so:

**Stage 1 — seeded random sample.** 300 packages drawn with `seed 20260806`, so anyone can
reproduce the exact sample.

| | count |
|---|---|
| sampled | 300 |
| unreachable / deleted | 8 |
| no direct `mcp` dependency (wrappers, clients, unrelated names) | 80 |
| **genuine Python MCP servers** | **212** |
| **of those, SDK left UNCAPPED** | **183 = 86.3%** (95% CI 81.0-90.3%) |
| properly capped | 29 |

**Stage 2 — real installs.** Uncapped is *necessary but not sufficient*: a server may have
migrated its code to mcp 2.x and simply left a loose pin. So a random 30 of the 183 were each
installed into a fresh virtualenv and their entry points executed.

**14 of the 28 that installed failed to start — 50%** (95% CI 32.6-67.4%).

**Combined population estimate: 86.3% x 50% ≈ 43%**, rough bounds 26-61%.

### Stage 2 is the point, not a formality

It **cleared three packages** that looked broken on metadata and start fine:
`mcp-server-obsidian`, `mcp-server-duckdb`, `mcp-server-bigquery`. Five more resolved to
mcp 1.29.0 despite an uncapped declaration, because a *transitive* dependency capped the SDK.

Reporting any of those as broken would have been wrong, and reporting them is exactly what
publishing the metadata number alone would have produced.

## A separate, higher number for established servers

23 well-known servers — Anthropic's, Microsoft's, and widely-used community ones — were checked
the same way. **18 of the 21 that installed failed: 86%.**

This is a **different population** from the random sample and is reported separately rather than
blended into the headline. If you quote one number, quote 43%; 86% describes established
packages specifically.

Counterintuitively the better-known servers fared worse. Stated as an observation, not a law:
the plausible reason is age — they were written early against mcp 1.x and nobody has reinstalled
them from scratch since. `mcp-server-git` shipped a release in July 2026 and still declares
`mcp>=1.0.0`.

**Tested for, and not found:** that broken packages are simply abandoned. Median days since last
PyPI release — **broken 237, working 248.** Broken packages are marginally *fresher*, and one had
shipped a release the day before testing. This is a live problem, not rot.

## One cause, three signatures

Every SDK-caused failure declares the MCP SDK with a lower bound and no upper bound
(`mcp>=1.0.0` and similar). The Python SDK released 2.0 and removed the APIs these servers call.

| error | example packages |
|---|---|
| `ModuleNotFoundError: No module named 'mcp.server.fastmcp'` | weather, calculator, redis, pubmed, yfinance, prometheus |
| `ImportError: cannot import name 'McpError' from 'mcp.shared.exceptions'` | time, fetch, shell, jira, neo4j |
| `AttributeError: 'Server' object has no attribute 'list_tools'` / `'list_resources'` | git, sqlite, playwright, notion, ssh |

One case has a different root cause: `mcp-server-sentry` fails with
`ModuleNotFoundError: No module named 'httpx'` — it imports `httpx` but never declares it, having
relied on mcp 1.x pulling it in transitively.

## Why maintainers can't see this

Their machine already satisfies `mcp>=1.0.0`, so `pip install` never upgrades anything.
**It only breaks for new users** — the person trying the server for the first time, who hits an
import error that looks nothing like a dependency problem, and doesn't come back.

## The fix

```toml
mcp>=1.0.0,<2      # instead of mcp>=1.0.0
```

Verified on all 18 established failures and 12 of the 14 random-sample failures: reinstalled with
`mcp<2` and re-run, each then started normally. (The other two failed for unrelated reasons — a
missing `yaml` dependency and a missing `src` module.)

## Reproducing this

```bash
python survey_unbounded.py      # metadata screen
python random_sample.py 300     # seeded random sample + Wilson intervals
python verify_install.py        # fresh venv per package, real install, entry point, fix check
```

Raw results are committed: `verify_results.json`, `verify_results_handpicked23.json`,
`random_sample_results.json`. The population list is regenerable from PyPI's index in seconds and
is not committed (366 KB).

**Nothing is fuzzed. No third-party server is contacted.** This is `pip install` plus a process
start with stdin closed — the gentlest check that exists.

## Limitations

- Servers not on PyPI, and Node/TypeScript servers, are out of scope. An earlier 13-server audit
  (`FINDINGS.md`) found **0 of 10 Node servers** affected — npm's lockfile conventions prevent
  this class of failure.
- Packages whose entry point needs credentials to start cannot be classified this way.
- The random sample's population is "packages with `mcp` in the name", which includes automated
  republications of other people's code. That is the real ecosystem, but it is not the same as
  "servers people actually use" — which is why the established-server figure is reported apart.

## A note on reporting these

Of the 18 established failures, **only one had an active repository accepting issues.** Several
are automated republications with no real GitHub presence; others point at repositories that were
archived or had issues disabled. That most of these cannot be reported is part of why they stay
broken.
